# Treg 連携の設計

外部データ(記事本文・RSS のないページ)の取得に Treg(API ゲートウェイ)を使う。
**予算は 1 回の実行あたり 約1円($0.0065)**。Treg が使えないときは、今まで通り RSS だけでサイトを生成する。

## 使うエンドポイント

| 用途 | エンドポイント | 単価 | 備考 |
|------|---------------|------|------|
| 記事本文の取得 | `litescrape.web.fetch.post` | $0.00015 / 成功 1 回(失敗は無料) | 計測上の成功率 約90%、p50 約15秒 |
| ページの変化 | 同上(毎日取得して前回と diff) | 同上 | 下記「crawl4ai.watch を使わない理由」 |

### 動作確認の結果(2026-11-27、MCP 経由で各 1 回)

| エンドポイント | 結果 | 実費 |
|---------------|------|------|
| `litescrape.web.fetch.post`(huggingface.co/blog) | 200。本文 Markdown を取得 | $0.00015 |
| `crawl4ai.watch.create`(githubstatus.com、毎日) | 201。ただし監視は作成直後から `paused_by: credit_limit` | $0 |
| `crawl4ai.watch.get` | 200(上と同じ状態) | $0 |
| `crawl4ai.watch.delete`(試験用の監視を削除) | 200 | $0 |

### crawl4ai.watch を使わない理由

カタログ上「作成は無料」だが、実際のページ確認は別途購入する **watch 予算** から引かれる
(確認 1 回 = 1 クレジット = $0.001、変化を検知すると +3 クレジット = $0.003)。
予算を買っていない状態では監視が一時停止のまま動かない。予算を買っても、4 ページを毎日確認するだけで $0.004/日、
変化が 1 件あれば $0.007/日となり、1 日 約1円($0.0065)を超える。
そのため引き継ぎ書の代替案どおり、**本文取得(litescrape)で毎日ページを取得し、前回のテキストと diff を取る**方式にした
(4 ページで $0.0006/日)。

## 呼び出し(`treg_client.py`)

- GitHub Actions から HTTP で呼ぶ。`Authorization: Bearer $TREG_API_KEY`
- 呼び出し先 URL は `TREG_API_URL`(Actions の **Variables**)。`{endpoint}` を含めばそこにエンドポイントIDを入れ、
  含まなければ末尾に `/<エンドポイントID>` を付ける
- **全呼び出しに料金上限** `X-Treg-Route-Max-Cost`(= カタログ単価)を付ける。見積もりが上回れば Treg が課金前に 402 で断る
- **1 回の実行の合計上限** `TREG_BUDGET_USD`(既定 0.0065)。呼ぶ前に見込み額を予約し、超えるなら呼ばない(並列でも超えない)
- 実費は応答ヘッダー(`X-Treg-Cost` など)→ 本文の `cost_usd` → カタログ単価 の順で精算する
- 401/403 → 以降の呼び出しを止める。その他の失敗 → その 1 件だけスキップ(キーや応答本文はログに出さない)
- 実行ログとジョブサマリーに `Treg: 呼び出し N回(成功 / 失敗 / 予算超過で中止) 合計 $x / 上限 $0.0065` を出す

> **要確認**: Treg の HTTP API のドキュメントはこの改修の作業環境から参照できなかった。
> 上の URL の組み立て方・ヘッダー名・実費ヘッダー名は MCP ツールの説明(`X-Treg-Route-Max-Cost` を含む)から推定したもの。
> `TREG_API_URL` を登録するときに、Treg のドキュメントで「エンドポイントIDを指定して呼ぶ URL」を確認し、
> 必要なら `{endpoint}` を使った形で登録する。実費ヘッダーが別名でも、カタログ単価で積算するので上限は守られる。

## 1. 記事本文 → 要約(`enrich.fetch_bodies`)

- 対象: RSS の概要が 20 文字未満の記事(人気記事・ページの変化は除く)。英語(海外記事)→ 新しい順に優先
- **1 日 20 件まで**、かつ予算の残りで払える件数まで
- 本文 Markdown から本文らしい段落(40 文字以上・メニュー等を除く)の冒頭 1〜2 文を取り、英語なら翻訳して約 110 文字(2 行程度)に
  - Jev は文章を生成しない(型付きの答えだけ返す)ため、要約は **抽出 + 翻訳** で作る
- 画面では「本文から要約」ラベルを付けて RSS 由来の概要と区別する
- 本文の先頭 800 文字を Jev の `state.body` に渡し、重要度判定にも使う
- **キャッシュ** `data/body-cache.json`(gh-pages): URL 単位。成功は要約と本文抜粋、失敗は回数を保存。
  2 回失敗した URL は取得しない。14 日で削除

## 2. ページの変化(`enrich.check_watches`)

- 監視対象は `feeds.yml` の `watches:`(`name`, `url`, `kind: status|price|terms|news`)。PR で追加できる(`scripts/validate_feeds.py` で検証)
- 各ページを **20 時間に 1 回まで** 取得(1 日に何度ワークフローが走っても 1 回)
- テキストを行に分け、時刻・日付・「3 minutes ago」などを伏せてから、前回の行と diff を取る(並び替えだけの変化は無視)
- 削除行 → 「変更前」(取り消し線)、追加行 → 「変更後」。見出しは `[名前] 種類:追加行の先頭`
- 種類ラベル: status=障害 / price=料金 / terms=規約 / news=発表。Lv は status/price/terms=4、news=3(Lv5 の相対評価の対象外)
- 検知した変化は 36 時間表示し、7 日で削除。取得に失敗した日は前回の内容を維持する(誤検知を出さない)
- 初回は基準として保存するだけ(変化は出ない)
- **スナップショット** `data/watch-snapshots.json`(gh-pages)

## 費用の見積もり

| 項目 | 回数/日 | 金額/日 |
|------|---------|---------|
| ページの変化(4 ページ) | 4 | $0.0006 |
| 本文取得(上限 20 件) | ≦20 | ≦$0.0030 |
| 合計 | ≦24 | **≦$0.0036**(上限 $0.0065) |

失敗は課金されない。上限に達した場合は、それ以降の呼び出しをせずにサイトを生成する。

## 設定

| 名前 | 種別 | 内容 |
|------|------|------|
| `TREG_API_KEY` | Secret | Treg の API キー。未設定なら Treg を使わない |
| `TREG_API_URL` | Variable | 呼び出し先 URL(上の「要確認」を参照)。未設定なら Treg を使わない |
| `TREG_BUDGET_USD` | 環境変数(任意) | 1 回の実行の上限。既定 0.0065 |
